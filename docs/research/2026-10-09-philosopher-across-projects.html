Where philosopher pages help across four repos, and what to work on next

Use philosopher for two jobs: explaining a mechanism or design that is slow to rebuild from code, and laying out an owner decision that has real trade-offs. Never use it in place of Markdown that an agent executes, ticks off, commits against, or that orch hashes or reads by path. The work that matters most right now is not a page. Finish the passkey deploy in order, run orch's first real request, and answer the four decisions that block similar collections (D1 to D4). Pages are for explaining and deciding; Markdown stays for the work

The owner asked how to use philosopher across memory, orch (which the owner calls "arch"), edens.zac and edens.zac.backend, and what those repos should focus on next. The first answer is narrow. The second has little to do with the skill.

A philosopher page helps a reader understand something once. That fits two kinds of document here. One is a mechanism that is slow to rebuild from code, such as frontend row composition, a 1,883-line file [rowCombination.ts]. The other is an owner decision with several real options [decision table, 401-432].

A page must never replace a file that an agent executes, ticks, commits against, or that orch hashes or reads by path. Those files are the working record. orch binds each approval to a sha256 hash of the artifact [domain.md:183,207]. The backend cleanup tracker is edited by agents and checked by a gate script [tracker, 18-60].

The top priorities, in order. The ranked table near the end gives the reasons.

  2. Run orch's first real request, a small frontend change. It is the top stated goal and everything it needs is built.
  3. Answer D1 to D4 to unblock similar collections, then build the endpoint. D5 and D6 can wait.

  6. Fix the stale docs.

Philosopher is a pinned Markdown bundle with local fixes on top

Run it with one researcher per repo, one writer and one reviewer

Research for a page like this is judgment work: deciding what matters and which record is stale. The 2026-10-08 ruling keeps Haiku to small repeatable tasks with checkable output, so researchers run on Sonnet [decisions 2026-10-08]. Name the model in each dispatch, since the same day's audit found 43% of dispatches inherit the parent's model [observations 2026-10-08]. Each researcher returns notes as claim, source and pointer [local-rules.md, Research across repos]. The writer works only from those notes. The reviewer opens the cited file for every claim the page leans on.

This strategy paper was made this way: one research subagent per repo plus a review of the skill, then one writer, then a reviewer. The writer opened a handful of cited files and found four places where the notes and the files disagree. Two are in the table above. The third is the similar-collections data gaps. The fourth is CT D2, which a mempalace entry from 2026-09-05 lists as open and the backend tracker dismissed the same day: the method in question was deleted on 2026-07-26 and new collections default to unlisted [:314-321]. The reviewer then checked about 62 claims and found more, including the passkey order and which decisions block similar collections. That rate of error is the reason the reviewer step exists.

Pages go stale as the repos move. Put the date and each repo's last commit date in the eyebrow or deck. Keep pages in docs/research/. When the mechanism a page explains changes, delete or regenerate the page. Do not add a correction beside the old text.
